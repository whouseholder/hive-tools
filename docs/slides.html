Why these tools exist

The metastore's MySQL DB is a shared, single-writer bottleneck. Two things degrade it:

  • Row bloat - data deleted straight off storage leaves orphaned table/partition rows behind in MySQL. Millions of dead rows slow every plan, backup, and upgrade.
  • Call pressure - badly-shaped workloads flood the HMS with API calls; each is a MySQL round-trip, so metadata gets slow for everyone.
flowchart LR
  B["Row bloat"] --> DB[("MySQL metastore")]
  P["Call pressure"] --> DB
  DB --> S["Slow for everyone"]
  OC["Orphan Cleanup"] -. fixes .-> B
  PM["Pressure Monitor"] -. diagnoses .-> P

The two tools at a glance

ToolWhat it doesChanges the cluster?
Orphan Cleanup
hive_orphan_cleanup.py		 Finds & removes Hive tables/partitions whose storage is gone, using standard Hive DML - shrinking metastore row counts on MySQL. Only with --execute
read-only by default
Pressure Monitor
metadata_pressure_monitor.py		 Reads HMS logs to find what/who is overloading the metastore, correlates to Hive operations & likely queries/apps, and prescribes fixes. Never
strictly read-only

Both are dependency-free: copy one script to an edge node and run it.

Which tool, when?

flowchart TD
  Q{"What is the symptom?"}
  Q -->|"Slow / overloaded HMS"| PM["Pressure Monitor"]
  Q -->|"MySQL bloat; data gone"| OC["Orphan Cleanup"]
  PM -->|"churn on dead data"| OC
  OC -->|"still slow"| PM

Not the right tool when...

  • You want to tune MySQL itself or change Cloudera Manager configs.
  • You want to find unused tables - orphan = storage genuinely gone, not idle.
  • You expect it to apply fixes - the monitor only recommends.
  • You want to reclaim disk - cleanup removes metadata, not data.

Orphan Cleanup - what it does

Three modes; the recommended flow is report → review → apply.

ModeWhat it doesMutates?
reportEnumerate HMS, check storage, write CSV + JSON + summary.No
cleanDetect and clean. Dry-run by default.With --execute
applyClean exactly the rows in a prior (trimmed) report.With --execute

Cleanup is standard Hive DML (DROP TABLE / ALTER TABLE ... DROP PARTITION), which cascades away the backing rows in TBLS/PARTITIONS/SDS/... - the MySQL win.

Orphan Cleanup - how detection works

flowchart TD
  S["List parent dir once (cached hdfs -ls)"] --> C{"Parent listed OK?"}
  C -->|"no - transient"| SKIP["SKIP: indeterminate"]
  C -->|yes| P{"Object present?"}
  P -->|yes| KEEP["Not an orphan"]
  P -->|no| ORPH["Flag ORPHAN"]

Positive proof of absence

  • An object is flagged only when its parent lists successfully and it is genuinely missing.
  • Any indeterminate result (outage, NameNode blip) is skipped - a storage hiccup cannot manufacture orphans.
  • Listings are batched one per parent dir and cached, keeping load off Isilon.

Orphan Cleanup - safety model

flowchart TD
  O["Orphans"] --> RV["Re-verify (positive proof)"]
  RV --> T{"Table type?"}
  T -->|ACID| ACID["NEVER drop"]
  T -->|MANAGED| M{"--allow-managed?"}

Loosening one gate never weakens the others: --yes skips only the keystroke; ACID is never droppable.

Pressure Monitor - what it answers

  • Which HMS methods dominate call volume and total time?
  • Which Hive operations (DROP/ALTER/ADD PARTITION, CREATE/DROP TABLE, ANALYZE) drive them?
  • Which users, client IPs, tables, and HMS hosts contribute most?
  • How does load trend over time - where are the storms?
  • Which patterns look like loops / repetitive calls - and how to fix them?

For every finding it prints a concrete remediation: batching, partition pruning, breaking loops, delegation-token store, stats tuning, ...

Pressure Monitor - how a run works

flowchart TD
  D["Discover logs (.gz ok)"] --> PR["Prune by mtime"]
  PR --> SK["Seek to window start"]
  SK --> GT["Cheap substring gate"]
  GT --> PS["Fast parse"]
  PS --> AG["Aggregate"]
  AG --> DE["Detect: findings + fixes"]
  AG --> CO["Correlate to ops / sources"]
  DE --> RP["Report"]
  CO --> RP

Cheap → expensive, so most lines are discarded before any regex.

ModeUseMutates?
reportAnalyze a window; fan-out & incremental options.No
monitorScheduled tail with de-duplicated alerts.No
aggPer-node worker for SSH fan-out.No
  • Fast: a --last 1h scan of a multi-GB log runs in well under a second.
  • Incremental (--state-dir): re-runs parse only new bytes.
  • Fleet (--hosts): each HMS node parses its own logs.

Pressure Monitor - attributing the load

Beyond "which method is hot", the report names who/what to go fix: top contributors, and up to a Top-5 likely source per operation with a confidence score.

Evidence availableConfidenceShown as
user + table from HMS audit onlyranked, capped < 100%"NN%" (guess)
+ client op matched on table and timehigher %"NN%" + queryId / appId
single unambiguous driver100%CONFIRMED

Honest by design: HMS audit logs share no id with HS2, so attribution is a ranked guess unless HS2/YARN/Spark logs confirm it. Treat the Top-5 as leads.

Implementation highlights

Built for production

  • Python 3.6+, stdlib only - no install.
  • Verified on RHEL 8 / CDP 7.1.9.
  • Read-only by default; every drop is audited.
  • Third-party safety audit + automated test harness.

Built for repeated runs

  • Fast filtering + cached parsing (~16x faster timestamps).
  • Incremental re-runs (process only new log bytes).
  • Fleet fan-out over SSH - no central log collection.
  • Batched, cached hdfs -ls to spare Isilon.

Limitations & caveats

  • Scope: tuned for CDP 7.1.9 / Hive 3 on-prem (RHEL 8, Isilon, MySQL). Other versions untested.
  • Orphan Cleanup needs a healthy filesystem view - run when Isilon/HDFS + NameNode are healthy; the bulk guard is a backstop, not a substitute.
  • "Orphaned" ≠ "unused" - tables whose data still exists are never flagged.
  • Correlation is best-effort - a ranked guess with a confidence score unless client logs confirm it.
  • Logs must be readable & standard - parsing targets Cloudera PERFLOG + AUDIT lines; live tail reads uncompressed logs.
  • Change control - back up the metastore (MySQL dump) before large cleanups.

A safe end-to-end workflow

flowchart LR
  A["1. Monitor"] --> B["2. Report orphans (read-only)"]
  B --> C["3. Review and trim CSV"]
  C --> D["4. apply --execute (type 'yes')"]
  D --> E["5. Re-monitor"]

Diagnose with the monitor → remove dead metadata with cleanup → confirm the metastore got faster. Execution stays a human-reviewed step.
